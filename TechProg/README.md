# Технология программирования

## Проект курса — сквозной

В этом курсе не девять отдельных работ, а **один проект на весь семестр**.
Каждая лабораторная добавляет к нему вертикальный срез — новый слой или новую
сквозную возможность. Ничего не выбрасывается и не переписывается с нуля: то,
что появится на второй неделе, доживёт до защиты.

Поэтому папки вида `lab-01`, `hw-01`, `self-01` в этом курсе не используются —
их можно удалить. Вместо них один проект:

```text
TechProg/
├── docs/          глоссарий, границы, ADR, диаграммы (.mmd)
├── src/           модули по слоям
└── tests/
```

| Работа | Что появляется в проекте | Ветка |
|---|---|---|
| 1 | глоссарий, диаграммы, границы — **без кода** | `TechProg/lab-01` |
| 2 | домен: сущности, инварианты, тесты правил | `TechProg/lab-02` |
| 3 | сценарии, порты, тест-даблы | `TechProg/lab-03` |
| 4 | хранение, миграции | `TechProg/lab-04` |
| 5 | REST, обработка ошибок, OpenAPI | `TechProg/lab-05` |
| 6 | аутентификация, роли, политики | `TechProg/lab-06` |
| 7 | доменные события, outbox | `TechProg/lab-07` |
| 8 | вебхук, inbox, идемпотентность | `TechProg/lab-08` |
| 9 | архитектурные тесты, ADR, защита | `TechProg/lab-09` |

Каждая работа — **отдельный pull request**. Он вливается только после ревью.
Замечания правятся в той же ветке, а не следующей работой поверх.

Условия работ и техническое задание на семестр — на сайте курса:
<https://radilov-spsu.github.io/materials/TechProg/>

## Правила репозитория на весь семестр

- **Код только на английском**: имена типов, методов, тестов, файлов, веток.
  По-русски — комментарии, документация и сообщения коммитов, если так удобнее.
- **Диаграммы только на Mermaid**, файлами `.mmd` или блоками в markdown.
  Скриншот диаграммы не принимается: его нельзя ни отревьюить, ни изменить.
- Документы — markdown в `docs/`.
- Каждое решение, которое дорого поменять, фиксируется **ADR**: решение,
  рассмотренные альтернативы, почему выбрано это. Раздел с альтернативами
  обязателен.

## Что ожидается в сдаче

- рабочий код с внятной историей коммитов, а не один коммит «готово»;
- описание работы — в тексте pull request'а: что сделано, как собрать
  и запустить, что не получилось;
- сообщения коммитов, по которым виден ход работы.

> История коммитов — часть сдачи. Двадцать коммитов «fix» и финальный
> «всё готово» читаются одинаково плохо.

Проверяется каждая сдача по одному списку: проект поднимается одной командой,
тесты зелёные, архитектурные тесты зелёные, принятые решения описаны в ADR.

## Ветка и PR

```bash
git switch -c TechProg/lab-01
```

PR называйте `ТП, работа 1: <тема>`.

На защите вопрос будет не «что вы применили», а **«зачем здесь этот слой
и где он был бы лишним»**.
